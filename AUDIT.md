# Аудит-снапшот проекта «Чат»: карта для проверки

E2E-мессенджер: история сообщений живёт ТОЛЬКО на устройствах в зашифрованном
виде, сервер восстановить её не может принципиально. Этот репозиторий —
сфокусированная выборка кода для стороннего аудита: крипто-ядро, сервер-релей
и ядро Android-клиента (хранение, сеть, приём/отправка). UI, тесты клиента и
ресурсы осознанно исключены для снижения объёма.

## Главные инварианты (что обязано выполняться)

1. **Сервер не видит plaintext никогда.** Вся криптография — только в клиентах
   (`crypto/`). Go-релей (`go/`) оперирует непрозрачными блобами: проверяйте,
   что нигде нет попытки декодирования, логирования содержимого или ключей.
2. **Wire-формат платформо-независим, байт-в-байт.** Смена формата = смена
   векторных тестов (`crypto/src/jvmTest/.../VectorsTest.kt`). Старые клиенты
   обязаны читать новые конверты (опциональные поля, новые тип-байты
   деградируют в записи «не поддерживается»).
3. **В release-бинарь крипто-модуля не входит ни одна сторонняя библиотека**
   (тестовые зависимости — не в счёт); состав зависимостей клиента зафиксирован
   в `android/build.gradle.kts` (OkHttp, ZXing, WorkManager, Compose, org.json).
4. **Отправитель определяется только из Bearer-токена** (сервер), получатель —
   из крипто-конверта (клиент). Смешение источников идентичности — критический
   дефект.
5. **TOFU (доверие при первом контакте)**: смена ключей пира — видимое
   пользователю событие, молчаливная подмена невозможна (`Tofu.kt`,
   `KnownKeys.kt`, `SafetyCode.kt`).
6. **Медиа и журнал на диске — только шифроблобами** (AndroidKeyStore —
   ключ хранилища: `KeyVaultAndroid.kt`, `Stickers.kt`, `Media.kt`).
   Расшифрованные копии — только в памяти, кроме осознанного экспорта
   пользователем.

## Состав снапшота

| Каталог | Что это | Объём |
|---|---|---|
| `crypto/` | Крипто-модуль KMP: sealed box (P-256 + HKDF + AES-GCM), зашифрованный журнал, KeyVault, векторные тесты | 12 файлов |
| `go/` | Сервер-релей: auth (PBKDF2 + ротация Bearer), очередь блобов (TTL 30 дней, удаление при доставке), медиа-бакет, WS-нотификации, e-mail-дискавери | 17 файлов, ~3,3k строк |
| `android/` | Ядро клиента: приём/дрейн, outbox отправки, TOFU, sealed-хранилища, сеть | ~48 файлов |
| `project/` | Мастер-план и план крипты (контекст решений) | 2 файла |

### Ключевые точки проверки (по приоритету риска)

1. **`go/auth.go`, `go/store.go`, `go/memstore.go`, `go/pgstore.go`** — аутентификация,
   ротация токенов, потолки, обход лимитов; leakage содержимого в метрики/логи.
2. **`crypto/src/commonMain/.../SealedBox.kt`, `Hkdf.kt`, `Primitives.kt`, `E2E.kt`** —
   генерация/вывод ключей, nonces, AAD (привязка к chatId), повторное использование,
   сравнение за постоянное время, случайные источники.
3. **`crypto/src/jvmMain/.../MessageStore.kt`, `androidMain/.../AndroidMessageStore.kt`,
   `KeyVaultAndroid.kt`** — целостность журнала, дозапись/обрыв строк,
   wipe (безвозвратность), утечки plaintext на диск.
4. **`android/data/MessageRepository.kt`** (самый большой файл) — дрейн очереди:
   валидация отправителя до использования, дедуп, групповые конверты
   (не слить чужой состав), применение служебных событий (правка/закреп/удаление —
   только автор, A4), карантин.
5. **`android/data/Outbox.kt`, `android/media/OutboxSender.kt`** — отправка:
   на сервер уходит ТОЛЬКО зашифрованный staged-блоб (исторический P0: раньше
   расшифровывал до загрузки — уже закрыт, проверить регресс), fan-out групп,
   персистентность между рестартами.
6. **`android/net/RelayApi.kt`, `WsClient.kt`** — доверие ответам сервера,
   валидация логинов (регэксп), ошибки транспорта не глотают данные.
7. **`android/domain/Envelope.kt`, `MessageFormats.kt`, `MessageCodec.kt`** —
   строгий разбор мусора, потолки длин, кодировка.
8. **`android/ui/ShareActivity.kt`** — attack surface внешних интентов:
   только content://, наш FileProvider и приватные пути отвергаются.
9. **`android/data/Backup.kt`** — экспорт ключей: только по паролю,
   с явным предупреждением.
10. **`android/service/Notifier.kt`, `ConnectionManager.kt`** — утечки plaintext
    в уведомления (настройка «скрывать текст»), фон и wake.

### Потолки архитектуры (осознанные, не дефекты)

- Нет forward secrecy (план v1), нет presence/«был в сети».
- Группы — client-side fan-out: состав едет в каждом групповом конверте,
  сервер о группах не знает.
- Медиа: транзит TTL 30 дней на сервере, локальная зашифрованная копия —
  на устройстве (после истечения TTL не скачать — задокументировано).
- Локальные настройки (мьют, архив, папки, автосейв) по сети не синхронизируются.

## Как снапшот удерживается (правило на будущее)

Состав репозитория зафиксирован `.gitignore`: в git учитывается ровно аудитовая
выборка — белые списки перечисляют разрешённые файлы ядра (`data/`, `domain/`,
`media/`, `net/`, `service/`), а UI/Compose-слой (кроме `ui/screens/share/ShareActivity.kt`),
ViewModel-слой, ресурсы, тесты, `promts/`, `design/`, `docs/`, обёртка Gradle и
`proguard-rules.pro` навсегда исключены. Они остаются в рабочем дереве и
собираются локально, но в GitHub больше не попадают.

Отсюда следствия для разработки:

- Новый файл ядра не попадёт в репозиторий сам — добавьте его строку с «!»
  в `.gitignore` (или разово `git add -f путь`), иначе он останется локальным.
- Проверить, что пуш содержит только снапшот: `git ls-files | wc -l` — должно
  быть около 50 файлов и ни одного пути вне белых списков.
- Наружу уходит только сам снапшот: `./push-audit.sh` собирает его по
  `audit-manifest.txt` в отдельном staging-репозитории и пушит `origin/main`.
  Прямой push из рабочего репозитория запрещён локальным `pre-push` hook'ом
  (`.githooks/`, включается `git config core.hooksPath .githooks`; аварийный
  обход — `ALLOW_DIRECT_PUSH=1`), а сверка в скрипте не даёт разойтись
  манифесту и белому списку.
- Вернуть полный код клиента в любом месте: `git checkout <коммит до снятия
  с учёта> -- .` (файлы целы в истории; рабочие копии на месте). Учтите, что
  явный checkout пути ставит файл обратно в index (то есть снова берёт под
  учёт) — для простого просмотра старой версии используйте
  `git show <коммит>:<путь>`.

### Что и как проверяется в снапшоте

- Go-релей собирается и проходит тесты прямо в снапшоте: `cd go && go test ./...`
  (`go.mod` + `go.sum` включены — зависимостей только gorilla/websocket и pgx).
- Kotlin-части (`crypto/`, `android/`) — для чтения и ревью: обёртка Gradle,
  ресурсы и UI в снапшот не входят, локальная сборка снапшота не предполагается.
- Снапшот — single-коммит (force-push): история репозитория не является
  предметом аудита, предмет — содержимое дерева.
